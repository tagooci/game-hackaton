# Что нужно от карты для сценариев

Этот документ — чек-лист для автора карты и импортёра. Он описывает не
визуальные требования к Blender, а данные, которые сервер должен получить после
импорта, чтобы проверять сценарии ПДД.

Главное правило: **карта описывает постоянную реальность перекрёстка, сценарий
описывает конкретное упражнение**. Приоритет дороги, направление полосы,
стоп-линия и геометрия должны быть одинаковыми для всех сценариев, которые
используют этот перекрёсток.

## Что уже есть

Текущий импортёр уже формирует:

- `worldId` и `contentVersion`;
- чанки визуальных ресурсов;
- дорожные поверхности для физики;
- коллайдеры и потолки;
- узлы и полосы базового дорожного графа;
- `navigation.json`;
- границы и spawn мира.

Источниками являются Blender-файл и скрипты
[`client/scripts/import-blender-map.py`](client/scripts/import-blender-map.py) и
[`client/scripts/generate-road-map.mjs`](client/scripts/generate-road-map.mjs).
Сервер использует физические поверхности из
[`client/public/content/world/navigation.json`](client/public/content/world/navigation.json).

Визуальный GLB не является источником правил. Сервер не должен пытаться
восстанавливать стоп-линию или приоритет по названию mesh.

## Обязательные данные карты

### 1. Стабильная идентификация мира

После каждого импорта должны быть доступны:

```json
{
  "worldId": "compact-reference-b311ebce",
  "contentVersion": "748742ec48c695f4",
  "coordinateSystem": "babylon-x-right-y-up-z-forward",
  "units": "meters"
}
```

- `worldId` меняется, если меняется логика размещения дорог или навигация;
- `contentVersion` меняется при изменении опубликованных ресурсов;
- ID существующих перекрёстков и дорог не должны случайно меняться между
  косметическими импортами;
- координаты сервера и клиента должны совпадать: `x/z` в метрах, `y` вверх,
  `heading` в радианах.

### 2. Перекрёстки

Для каждого места, где может запускаться сценарий:

```json
{
  "id": "junction-01",
  "type": "crossroad",
  "bounds": {
    "minX": 48.0,
    "maxX": 68.0,
    "minZ": 10.0,
    "maxZ": 30.0,
    "minY": -0.5,
    "maxY": 1.5
  },
  "approaches": ["north", "south", "east", "west"],
  "conflictAreaIds": ["junction-01-conflict"],
  "laneIds": ["north-main-in", "south-main-in", "east-secondary-in"]
}
```

Нужно отличать перекрёстки, круговые движения, съезды и многоуровневые
пересечения. Под мостом и над мостом должны быть разные уровни, даже если их
проекция на X/Z пересекается.

### 3. Дороги и полосы

Для каждой полосы нужны:

- стабильный `id`;
- `roadId` и `junctionId`, если полоса относится к перекрёстку;
- направленная центральная линия;
- ширина;
- направление движения;
- входная и выходная сторона;
- разрешённые маршруты;
- уровень/этаж;
- базовый приоритет;
- ограничение скорости.

Пример:

```json
{
  "id": "north-main-in",
  "roadId": "north-south",
  "junctionId": "junction-01",
  "direction": "south",
  "level": 0,
  "width": 3.2,
  "centerline": [[58.5, 40.0], [58.5, 30.0], [58.5, 20.0]],
  "priority": "main",
  "speedLimit": 8.3333333333,
  "allowedRouteIds": ["north-to-south", "north-to-east"],
  "leftBoundaryId": "north-main-centerline",
  "rightBoundaryId": "north-main-curb"
}
```

Центральная линия должна быть направлена по движению. Несколько точек нужны
для кривых и поворотов; одной точки или только bounding box недостаточно для
проверки полосы.

### 4. Разметка и стоп-линии

Для каждой линии, которую может пересечь автомобиль:

```json
{
  "id": "east-secondary-stop",
  "kind": "stop_line",
  "from": [68.0, 18.4],
  "to": [68.0, 21.6],
  "level": 0,
  "allowedDirection": "west",
  "laneIds": ["east-secondary-in"],
  "ruleTags": ["must_stop_before_crossing"]
}
```

Нужны также:

- осевые линии;
- границы полос;
- линии, пересечение которых разрешено;
- линии, пересечение которых считается нарушением;
- направление допустимого пересечения;
- принадлежность линии полосе и уровню.

Для каждой линии должны быть концы отрезка или полилиния. Название и цвет
материала не заменяют геометрию.

### 5. Знаки и светофоры

Для знака или светофора нужны:

```json
{
  "id": "signal-east-01",
  "kind": "traffic_light",
  "position": [70.0, 1.8, 20.0],
  "heading": -1.5707963268,
  "laneIds": ["east-secondary-in"],
  "phases": ["red", "red_yellow", "green", "yellow"]
}
```

Минимальный набор для знаков:

- `id`;
- тип;
- позиция и ориентация;
- полосы или подходы, к которым знак относится;
- уровень;
- при необходимости зона действия.

Для светофора дополнительно нужны фазы и принадлежность сигналу конкретных
полос. Текущая игра ещё не управляет фазами светофоров, но карта должна
сохранить эти связи для будущей реализации.

### 6. Маршруты

Маршрут — это постоянная связь между входной и выходной полосой, а не роль
игрока в конкретном сценарии:

```json
{
  "id": "north-to-east",
  "junctionId": "junction-01",
  "fromLaneId": "north-main-in",
  "toLaneId": "east-main-out",
  "centerline": [[58.5, 30.0], [64.0, 24.0], [68.0, 20.0]],
  "allowed": true,
  "crossesLaneIds": ["junction-01-conflict"]
}
```

Маршрут должен позволять серверу определить, куда реально поехала машина,
даже если игрок не сообщил о намерении. Сценарий выбирает маршрут, а сервер
сравнивает фактическое движение с ним.

### 7. Зоны

Нужны геометрические зоны, а не только точки:

```json
{
  "id": "junction-01-approach-north",
  "kind": "approach",
  "shape": "box",
  "minX": 56.0,
  "maxX": 61.0,
  "minZ": 34.0,
  "maxZ": 44.0,
  "level": 0,
  "laneIds": ["north-main-in"]
}
```

Обязательные типы зон:

- `approach` — подъезд к перекрёстку и регистрация;
- `intersection` — внутренняя область перекрёстка;
- `exit` — выезд после перекрёстка;
- `return` — безопасная точка возврата после сценария;
- `stop` — область, где допустима проверка остановки.

Автомобиль может занимать площадь, поэтому сервер должен иметь возможность
проверить, что в зоне находится весь коллайдер, а не только его центр.

### 8. Приоритеты

Базовый приоритет хранится на карте:

```json
{
  "id": "north-south",
  "kind": "road",
  "priority": "main",
  "prioritySource": "road_sign",
  "approachIds": ["north", "south"]
}
```

Допустимые значения на первом этапе:

- `main`;
- `secondary`;
- `equal`;
- `signal_controlled`;
- `unknown`.

Если приоритет зависит от знака, светофора или динамической фазы, это должно
быть явно связано через `prioritySource` и ID соответствующего объекта.

Сценарий не должен переписывать базовый приоритет молча. Он может выбрать
участников и проверить отношение `yield_to`, но карта остаётся источником
постоянной дорожной ситуации.

### 9. Конфликтные области

Для проверки уступки нужна область, в которой маршруты пересекаются:

```json
{
  "id": "junction-01-conflict",
  "kind": "conflict_area",
  "polygon": [[54.0, 16.0], [63.0, 16.0], [63.0, 24.0], [54.0, 24.0]],
  "level": 0,
  "routeIds": ["north-to-south", "east-to-north"]
}
```

Она нужна, чтобы сервер мог сравнивать порядок въезда, а не только конечные
позиции. Для разных уровней дороги должны быть разные `level` и отдельные
конфликтные области.

## Проверки качества импорта

Импортёр должен проверять и сообщать ошибку, если:

- ID дублируются;
- полоса не имеет центральной линии или ширины;
- направление полосы не определено;
- маршрут ссылается на отсутствующую полосу;
- стоп-линия ссылается на отсутствующую полосу;
- зона выхода находится на другом уровне, чем маршрут;
- перекрёсток не связан со своими полосами;
- конфликтная область не связана с маршрутами;
- обязательные координаты не являются конечными числами;
- два разных объекта используют один ID;
- дорожный граф содержит разрыв, которого нет в визуальной карте.

Результат проверки должен содержать количество:

```json
{
  "validation": {
    "connected": true,
    "junctions": 1,
    "lanes": 8,
    "routes": 12,
    "stopLines": 4,
    "signals": 0,
    "conflictAreas": 2,
    "errors": []
  }
}
```

Ошибки импорта должны останавливать публикацию карты. Нельзя публиковать GLB с
неполными навигационными данными и молча отключать проверки сценариев.

## Что не нужно делать в Blender

Не нужно вручную рисовать в Blender отдельные невидимые меши для каждой проверки,
если эти данные можно экспортировать в JSON. Визуальная разметка может оставаться
моделью, но серверу нужны точные JSON-объекты.

Не нужно помещать в карту:

- роли игроков;
- порядок набора участников;
- тексты подсказок;
- XP и штрафы;
- конкретный состав упражнения;
- состояние текущей игровой сессии.

Эти данные относятся к сценарию и описаны в
[`SCENARIO.md`](SCENARIO.md).

## Минимальный результат для первой интеграции

Для одного перекрёстка достаточно предоставить:

1. один стабильный `junctionId`;
2. две входные и две выходные полосы;
3. две направленные центральные линии;
4. две зоны `approach`;
5. две зоны `exit`;
6. одну стоп-линию;
7. один базовый приоритет `main` и один `secondary`;
8. два маршрута;
9. одну конфликтную область;
10. одну безопасную зону `return` для каждого участника;
11. успешный отчёт валидации.

После этого можно подключить сценарий на двух игроках без изменения физического
движка. Третий участник и дополнительные повороты будут расширением данных.

## Приёмка карты сервером

Сервер принимает карту только если:

- `worldId` совпадает с `mapId` сценария;
- все ссылки сценария разрешаются в данных карты;
- spawn находится на своей входной полосе;
- destination находится на ожидаемой выходной полосе;
- маршрут имеет правильное направление;
- уровни дороги совпадают;
- зоны регистрации и возврата не пересекаются с опасными областями;
- геометрические проверки проходят на сервере.

Финальные данные должны быть опубликованы вместе с версией контента. После
изменения логической геометрии нужно увеличить `worldId`, чтобы сохранённые
позиции и старые сценарные ссылки не применялись к новой карте.
