# Контракт результатов сценария для ИИ-агента

Один JSON описывает результат одного игрока в одном прохождении. Для короткого и длинного сценария структура одинаковая.

Сервер формирует один объект на игрока после завершения прохождения. Значения проверок рассчитывает серверный алгоритм, а ИИ получает готовые факты для оценки и объяснения ошибок. Сейчас объект выводится одной JSON-строкой в stdout Python-сервера, без записи результата в БД или файл.

```json
{
  "schemaVersion": 1,
  "resultId": "result-unique-id",
  "sessionId": "session-42",
  "scenario": {
    "id": "left-turn",
    "version": 1,
    "type": "short"
  },
  "playerId": "p4",
  "roleId": "left-turn",
  "status": "completed",
  "durationMs": 24500,
  "checks": {
    "roadMarkings": {
      "checked": true,
      "violationCount": 0
    },
    "rightOfWay": {
      "checked": true,
      "violationCount": 1
    },
    "trafficSigns": {
      "checked": true,
      "violationCount": 0
    },
    "collisions": {
      "checked": true,
      "violationCount": 0
    }
  },
  "violations": [
    {
      "id": "violation-1",
      "category": "rightOfWay",
      "ruleId": "yield-to-oncoming",
      "timeMs": 12300,
      "position": {
        "x": 58.5,
        "y": 0.1,
        "z": 21.5
      },
      "relatedPlayerIds": ["p7"],
      "signId": null,
      "details": "Левый поворот создал помеху встречному автомобилю"
    }
  ]
}
```

## Проверки

| Поле | Что проверяет |
|---|---|
| `roadMarkings` | Запрещённое пересечение разметки. Разрешённое пересечение прерывистой нарушением не считается |
| `rightOfWay` | Соблюдение очередности проезда с учётом знаков и манёвров |
| `trafficSigns` | Остальные нарушения требований знаков. Одно общее количество для всех типов знаков |
| `collisions` | Столкновения с другими автомобилями |

## Правила контракта

- `scenario.type`: `short` или `long`.
- `status`: `completed`, `cancelled` или `timeout`. Завершение маршрута само по себе не означает правильный проезд.
- `checked: false` означает, что проверка не выполнена; тогда `violationCount: null`. Это нельзя трактовать как отсутствие ошибок.
- `violationCount` — число отдельных событий, а не кадров нарушения. Продолжительный контакт с машиной считается одним столкновением.
- Каждому нарушению соответствует запись в `violations`; количество записей категории совпадает с её `violationCount`.
- Неуступание по знаку относится к `rightOfWay` и повторно в `trafficSigns` не учитывается. При наличии знака указывается его `signId`.
- `resultId` уникален: повторная отправка того же JSON не создаёт повторную оценку.
- Все времена указаны в миллисекундах от начала управления в сценарии; координаты — в метрах.

Новые знаки добавляют новые значения `ruleId` и `signId`, сохраняя общее поле `trafficSigns.violationCount`. ИИ формирует оценку на основании этих данных, не меняя факты нарушений.

## Идентификатор прохождения

`sessionId` — уникальный идентификатор одного совместного прохождения сценария.
Сервер создаёт его при подборе пары: `scenario:left-turn:<UUID>`.
Оба игрока получают один sessionId; повторный запуск с той же парой получает новый UUID.
Идентификатор не меняется при индивидуальном финише и не совпадает с HTTP-cookie авторизации,
playerId, названием сценария или resultId. resultId уникален для отчёта каждого игрока.

## Текущее покрытие карты

Правила упражнения находятся в `client/public/content/scenarios/left-turn/scenario.json`, в поле `rules`.
Для текущего короткого упражнения явно описаны прерывистая осевая главной дороги и сплошная осевая на съезде. Внутри перекрёстка
разметка не продолжена воображаемой запрещённой линией: поворот разрешён.
Проверяется габарит кузова, движение между тактами сервера и физические контакты.
Отдельной категории laneChanges нет; пересечение запрещённой разметки учитывается в roadMarkings.

Знаки приоритета учитываются в rightOfWay без дублирования в trafficSigns.
Обработчики поддерживают priority, yield, speedLimit, stop, noEntry, allowedDirections;
неизвестный тип отклоняется при создании проверки. Для новых знаков нужны их зоны,
линии контроля, разрешённые роли и остальные параметры конкретного обработчика.
STOP не требует секундной остановки: достаточно фактической остановки перед линией.

Все четыре категории включены для текущего упражнения. Это не означает автоматического
покрытия произвольной новой карты или длинного сценария: им нужны собственные rules;
неописанные категории получают checked=false, violationCount=null.
Приоритет текущего упражнения проверяется по фактическому порядку выхода: сначала straight, затем left-turn.
Выход засчитывается, когда весь кузов пересёк границу выезда: z=15 для straight, x=55 для left-turn.
Прогноз времени сближения не используется. Это учебное правило очередности, а не универсальная проверка помех по ПДД.
Поле passageOrder содержит известный на момент отчёта порядок: playerId, roleId, timeMs.
В отчёте первого финишировавшего ещё может отсутствовать второй участник.
Если оба вышли за один такт, порядок определяется по времени пересечения внутри такта; одновременный выход не считается соблюдением строгой очередности.

## Автоматический вызов агента

После индивидуального финиша сервер передаёт сформированный отчёт в `submit_agent_result(report)`.
Фоновая задача проверяет его через `parse_result`, вызывает `OllamaFeedbackGenerator.generate`
и отправляет `agent_feedback` только исходному WebSocket-соединению игрока.
Содержимое: `resultId`, `sessionId`, `playerId`, `feedback`.
Если локальная модель недоступна, отправляется `agent_feedback_error`, а ошибка записывается
в консоль сервера. Финиш и возвращение на карту не ждут генерации.
Результаты и ответы в этом пути не сохраняются в БД. При отключении клиента ответ
не пересылается другому подключению и не сохраняется для последующего получения.
Отменённые прохождения автоматически агенту не отправляются.

Клиент принимает сообщение и публикует `window`-событие `agent-feedback` с сообщением
в `event.detail`; ответ также виден в консоли браузера. Отдельного экрана ответа пока нет.
Клиент не отправляет собственные факты нарушений через `agent_result`.

Запуск сервера с установленной локальной моделью:

```bash
cd /Users/tagooc/game-hackaton
OLLAMA_MODEL=qwen3.5:4b .venv/bin/python -m uvicorn server.app:app --host 0.0.0.0 --port 8000
```

Ollama должен быть доступен локально по `OLLAMA_URL` (по умолчанию
`http://127.0.0.1:11434`). По умолчанию в модуле агента выбрана `qwen3.5:2b`;
через `OLLAMA_MODEL` нужно указать реально установленную модель. Скачивание модели
при завершении проезда не выполняется.
