## Протокол клиент-сервер, версия 1

Единый источник правды для сервера (Б.), клиента (Ильяз) и snapshot (Андрей). Если код и этот файл расходятся, прав файл, код нужно исправить.

## Правила изменений (заморозка)

Всё, что описано в разделах "Сообщения" и "Общие правила", заморожено.

- Нельзя: переименовывать поля и типы сообщений, удалять их, менять тип значения, единицы измерения или смысл.
- Можно: добавлять новые типы сообщений и новые необязательные поля в существующие сообщения.
- Получатель (и клиент, и сервер) обязан игнорировать неизвестные поля и неизвестные `type`. Это единственное, что позволяет добавлять новое, не ломая старое. Неизвестный `type` от клиента сервер не обрабатывает, а отвечает `error` с кодом `unknown_type`.
- Любое добавление сначала дописывается в этот файл (раздел "Дополнения"), потом кодится. Добавление делает тот, кому оно нужно, и сообщает остальным.
- Если когда-нибудь понадобится ломающее изменение, это будет протокол версии 2 на новом адресе, а версия 1 продолжит работать.

## Общие правила

- Транспорт: WebSocket, адрес `ws://<IP сервера>:8000/ws`. Один эндпоинт на все сообщения.
- Формат: текстовые JSON-сообщения, у каждого есть строковое поле `type`.
- Единицы: метры и радианы. Числа округляем до 2 знаков.
- Оси (Babylon.js, левосторонняя система): x вправо, y вверх, z вперёд. Движение по земле описывается парой `x`, `z`. Высота `y` в версии 1 не передаётся (считается, что игрок стоит на земле).
- `heading` - поворот вокруг оси y в радианах. 0 означает взгляд в сторону +z. Значение совпадает с `mesh.rotation.y` в Babylon.js, пересчитывать не нужно.
- `id` игрока выдаёт только сервер, строка вида `"p1"`, `"p2"`. Клиент его не придумывает.
- `name` - строка, сервер обрезает пробелы по краям, длина 1-24 символа.
- `zone` - строка. Сейчас всегда `"world"`. В будущем бывает `"room:<имя>"`. Клиент в версии 1 просто сохраняет значение и не опирается на него.
- Частота: клиент шлёт `state` примерно 20 раз в секунду, сервер шлёт `snapshot` примерно 20 раз в секунду.
- Границы платформы, точка спавна, лимит скорости - это настройки сервера, а не часть протокола. Они могут меняться, формат сообщений от этого не меняется. Сервер ограничивает `x`, `z` границами сам.

## Сообщения

Порядок общения: подключился к `/ws` -> клиент шлёт `join` -> сервер отвечает `welcome` -> клиент начинает слать `state`. До `join` сервер принимает только `join`, всё остальное отклоняет ошибкой `not_joined`. `state` до получения `welcome` слать не нужно.

Клиент -> сервер:

```
{ "type": "join", "name": "Ilyaz", "v": 1 }
{ "type": "state", "x": 1.25, "z": -3.40, "heading": 1.57 }
```

- `join`: `name` (строка), `v` (число, версия протокола, сейчас 1). Отправляется один раз.
- `state`: `x`, `z`, `heading` - текущая позиция своего игрока. Сервер ничего не отвечает на каждое `state`, результат виден в следующем `snapshot`.

Сервер -> клиент:

```
{ "type": "welcome", "id": "p1", "zone": "world", "x": 0, "z": 0, "heading": 0,
  "players": [ { "id": "p2", "name": "Andrey", "zone": "world", "x": 5, "z": 2, "heading": 0 } ] }

{ "type": "snapshot", "tick": 1234,
  "players": [ { "id": "p1", "x": 0.5, "z": 1.2, "heading": 0.3 },
               { "id": "p2", "x": 5.0, "z": 2.0, "heading": 0 } ] }

{ "type": "player_joined", "id": "p2", "name": "Andrey", "zone": "world", "x": 0, "z": 0, "heading": 0 }

{ "type": "player_left", "id": "p2" }

{ "type": "error", "code": "bad_message", "text": "пояснение для разработчика" }
```

- `welcome`: ваши `id`, стартовая позиция (`zone`, `x`, `z`, `heading`) и список игроков, которые уже в игре (без вас). Клиент после этого создаёт своего персонажа и персонажей из `players`.
- `snapshot`: все игроки, которых вы должны видеть, включая вас самого. Клиент по `id` пропускает свою запись при отрисовке чужих. `tick` - номер тика сервера, увеличивается на 1 (нужен для интерполяции и отладки). Имён в `snapshot` нет, их берут из `welcome` и `player_joined`. Если игрока нет в `snapshot`, но он не отправил `player_left`, его не удаляют, ждут следующего снапшота.
- `player_joined`: появился новый игрок. Клиент создаёт персонажа и запоминает имя по `id`.
- `player_left`: игрок вышел. Клиент удаляет персонажа и забывает `id`.
- `error`: `code` из списка ниже, `text` для человека. Клиент выводит в консоль, не падает.

Коды ошибок: `bad_message` (не JSON или не хватает полей), `bad_value` (не число, NaN, слишком длинное имя), `unknown_type`, `not_joined`, `already_joined`, `bad_version` (после этой ошибки сервер закрывает соединение).

## Правила интерполяции и валидации

- Сервер считает позицию в `state` верной, если `x`, `z`, `heading` - конечные числа. Иначе отвечает `bad_value`, а позицию не меняет.
- Сервер может ограничить `x`, `z` границами платформы. Если вас "прижало" к границе, в `snapshot` придёт скорректированная позиция, клиент должен её принять.
- Сервер никогда не рассылает позиции внутри обработчика `state`, только в тике. Это значит, что клиент не должен ждать ответа на каждое своё `state`.
- Чужих игроков клиент рисует с небольшой задержкой (порядка 100 мс), интерполируя между двумя последними снапшотами. Реализация на стороне клиента (Андрей и Ильяз договариваются между собой), на формат протокола не влияет.

## Дополнения

Зарезервированы на будущее. Эти имена нельзя использовать для чего-то другого. Точный формат допишется сюда, когда дойдём до реализации.

- Авторизация: необязательное поле `token` в `join` (или отдельное сообщение `auth` перед `join`). Существующие поля не меняются.
- Зоны и комнаты: `enter_building` (клиент -> сервер, поле `doorId`), `exit_building` (клиент -> сервер), `zone_change` (сервер -> клиент, поля `zone`, `x`, `z`, `heading`). После `zone_change` сервер присылает в `snapshot` только игроков из вашей зоны. Файлы комнаты клиент забирает по HTTP, а не через сокет.
- Чанки: `chunks` (сервер -> клиент, списки `load` и `unload`).
- Чат: `chat` (в обе стороны, поле `text`).
