# Протокол v2: автомобили и совместные сценарии ПДД

Дата: 2026-10-31. Статус: согласованный исходный контракт для реализации новой концепции.

**Реализованный этап:** авторизация HTTP-cookie и `/ws/v2`, bootstrap с размерами
локальных ресурсов, prepare/ready/start общего мира, серверная физика 30 Гц,
input и полные snapshot 20 Гц, отображение всех машин, сохранение позиции в SQLite,
а также базовый серверный реестр сценариев с ожиданием участников, назначением ролей
и фиксацией прибытия участников в индивидуальные финишные зоны.
Переход в отдельную сцену, запуск после готовности всех участников, правила и
контроль 10% кэша ниже остаются целевым контрактом.
План содержит sedan.glb и colormap.png, а `plan.mapManifestUrl` указывает на
`/content/world/manifest.json`. Первая область карты загружается до scene_ready;
следующие клиент выбирает по положению машины. Bootstrap worldBytes включает
ресурсы дорожного манифеста и игровой машины; cacheBudgetBytes — worldBytes // 10.
Общий бюджет пока не обеспечен; дорожный загрузчик ограничивает только свои ресурсы.

Единственный игровой WebSocket — `/ws/v2`.

## 1. Распределение ответственности

| Область | Ответственность |
| --- | --- |
| Python-сервер | Физика, столкновения, положение машин, зоны, подбор участников, роли, правила ПДД, результаты, сохранение |
| Браузер / Babylon.js | WASD, отправка управления, загрузка ресурсов, модели, камера, интерфейс, интерполяция |
| Автор карты | Геометрия, чанки, полосы, знаки, общие ресурсы и совпадающие с графикой данные для серверной логики |
| Автор сценария | Шаблон перекрёстка, роли, точки появления, правила и условия завершения |

Клиент не назначает себе позицию, роль или результат. КамАЗ и легковая машина
используют один алгоритм аркадной физики с разными конфигурациями.
GLB — визуальный ресурс, а не описание правил: Python читает отдельные JSON-данные.

## 2. Транспорт, единицы и идентификаторы

- HTTP API: `/api/v2/...`; WebSocket: `ws://<сервер>:8000/ws/v2`.
  Для HTTPS используется WSS. Все библиотеки, декодеры, модели и ИИ работают локально.
- WebSocket: текстовый JSON-объект со строковым `type`. Максимум 16 КиБ на сообщение клиента;
  файлы мира передаются по HTTP, не в WebSocket. Размер входящих пакетов проверяет сервер.
- Неизвестные поля игнорируются. Неизвестный тип от сервера клиент игнорирует;
  сервер отвечает на неизвестный тип клиента ошибкой `unknown_type`.
- Обязательные поля обязательны даже при значении 0. Числа конечные, boolean не считается числом.
  `NaN` и `Infinity` запрещены. Все счётчики — целые 0..9007199254740991.
- Расстояния и размеры — метры, скорость — м/с, углы — радианы. Для интерфейса км/ч = м/с × 3.6.
  Расчёты выполняются без округления. В snapshot координаты, скорость и углы округляются
  до 3 знаков; для сравнения и правил используются исходные значения сервера.
- Левосторонние оси Babylon.js: Y вверх, X вправо, Z вперёд. `heading=0` направлен в +Z;
  положительный угол поворачивает к +X. Heading нормализован в диапазон [-π, π).
- `x,z` — центр прямоугольного основания машины. Визуальная модель привязана к этой
  точке на уровне земли; модель и коллайдер не должны использовать разные центры.
  V2 первой реализации — плоский мир: Y земли = 0, высота по сети не передаётся.
- `playerId` — стабильный серверный ID учётной записи. `connectionId` — ID текущего
  соединения; его нельзя использовать как ID машины или как постоянную память игрока.
  На игрока допускается одно активное соединение; новое закрывает старое кодом 4001.
- У игрока одна управляемая машина. Её состояние находится в записи игрока.
  `vehicleType` — ключ конфигурации (`car`, `truck`), `roleId` — роль сценария или null.
- `mapId` — шаблон карты/перекрёстка. `sceneId` — конкретный экземпляр:
  `world:main` или, например, `scenario:s42`. Один mapId может иметь много независимых sceneId.
- `epoch` — номер загрузки сцены для конкретного соединения. Начинается с 1,
  увеличивается при каждой смене сцены, включая возврат в тот же общий мир.
  После нового соединения начинается заново; старые сообщения не переносятся между соединениями.
- `tick` — общий номер шага симуляции процесса сервера; после перезапуска начинается заново.
  Идентификаторы и версии контента — непрозрачные строки, их формат клиент не разбирает.

## 3. Частоты и модель движения

Начальные настройки: Python считает физику с фиксированным шагом 1/30 с, клиент
отправляет управление 20 раз/с, сервер рассылает snapshot 20 раз/с. Реальные значения
приходят в `welcome`. Сетевые отправки и симуляция — отдельные циклы: не округлять
отношение 30/20 до «каждый второй тик». Отрисовка идёт по частоте экрана.

Функция автомобиля не зависит от FastAPI:

`step_vehicle(state, controls, config, dt) -> new_state`

Состояние: x, z, heading, speed. Speed — продольная скорость со знаком:
положительная вперёд, отрицательная назад. Конфигурация содержит wheelbase,
length, width, maxForwardSpeed, maxReverseSpeed, acceleration, brakeDeceleration,
rollingDeceleration, maxSteerAngle. Размеры положительные, скорости и ускорения —
неотрицательные. Центр, знаки руления и единицы соответствуют разделу 2.

Первая версия использует серверный расчёт без клиентского предсказания. Клиент
применяет серверное состояние и своей машины, а не только чужих. Камера следует
за отображаемой машиной. Интерполяция — около 100 мс по времени получения snapshot;
heading интерполируется по кратчайшей дуге. После разрыва истории и смены сцены
интерполяционный буфер очищается, между сценами движения не интерполируются.
Если новых данных нет, отображается последняя известная позиция без бесконечной экстраполяции.
Для определения обрыва сервер использует WebSocket ping/pong транспорта (интервал
10 секунд, ожидание pong 10 секунд); игровые сообщения для heartbeat не требуются.

Предсказание — отдельное последующее дополнение. `lastInputSeq` подтверждает
использование команды, но не задаёт её длительность: одного этого поля недостаточно
для точного повторного проигрывания команд на клиенте.

Возврат на общий спавн: клиент посылает
`{"type":"respawn","sceneId":"world:main","epoch":1}` по нажатию R.
Сервер принимает запрос только для готового игрока в общем мире с актуальным
контекстом. В сценарии возвращает `respawn_forbidden`. Координаты клиент не задаёт.
Сервер сбрасывает скорость, руление и ввод, увеличивает epoch и отправляет
`scene_prepare` с позицией спавна. Далее обычные `scene_ready` → `scene_start`: до
загрузки дороги машина неподвижна, старые input игнорируются. Позиция сохраняется.
Общий спавн задают `spawn` и `spawnY` манифеста карты; новые игроки начинают там.


## 4. Авторизация и подключение

Сначала HTTP-вход, затем WebSocket. `join` сам по себе не является авторизацией.
Для первой версии аккаунты заранее создаются на сервере, отдельная регистрация не нужна.

`POST /api/v2/login`:

```json
{ "username": "ilyaz", "password": "local-password" }
```

Успех 200, тело:

```json
{ "playerId": "p17", "name": "Ильяз" }
```

Сервер устанавливает непрозрачную сессионную cookie `game_session`: HttpOnly,
SameSite=Lax, Path=/; Secure включён при HTTPS. Пароли хранятся как хеши.
`GET /api/v2/me` возвращает тот же объект или 401; `POST /api/v2/logout`
удаляет сессию и закрывает её игровые соединения. Неверный логин — 401.

Для локальной игры допускается первичная регистрация через:

`POST /api/v2/register`:

```json
{ "username": "ilyaz", "password": "local-password", "name": "Ильяз" }
```

Успех имеет тот же ответ и cookie, что и login. Повторный username даёт 409,
неверные поля — 400. Владелец сервера может отключить регистрацию на уровне
прокси или сети, оставив создание аккаунтов через `server.manage_users`.

В разработке клиент обращается по относительным URL: Vite проксирует `/api/v2`
и `/ws/v2` в FastAPI, включая WebSocket и cookie. В готовой сборке FastAPI/прокси
раздаёт всё с одного origin. Это целевая настройка v2, её ещё нужно реализовать.
Сервер проверяет сессию и допустимый Origin до допуска к игровым сообщениям.
Неавторизованное соединение отклоняется; если upgrade уже выполнен — код 1008.
Токены не передаются в URL. Имя из query-параметров не заменяет имя учётной записи.

Порядок:

1. HTTP-вход → открытие `/ws/v2`.
2. Клиент отправляет `join` один раз, сервер проверяет версию и присылает `welcome`.
3. Сервер присылает `scene_prepare`, клиент загружает контент и отвечает `scene_ready`.
4. Сервер присылает `scene_start`; управление разрешается с указанного тика.

Клиент → сервер:

```json
{ "type": "join", "v": 2 }
```

Сервер → клиент:

```json
{
  "type": "welcome",
  "v": 2,
  "playerId": "p17",
  "connectionId": "c91",
  "name": "Ильяз",
  "tick": 100,
  "simulationHz": 30,
  "snapshotHz": 20,
  "inputHz": 20,
  "inputTimeoutMs": 250,
  "contentUrl": "/api/v2/content/bootstrap"
}
```

`join` должен прийти за 5 секунд после подключения, `welcome` — за 5 секунд после join.
При тайм-ауте соединение закрывается. После транспортного сбоя клиент обнуляет ввод,
очищает чужие машины и повторяет подключение через 3 секунды. Повторный 401/1008
возвращает форму входа; 4001 показывает, что аккаунт открыт на другом клиенте, без
автоматической борьбы за соединение. Каждый reconnect проходит весь handshake заново.

## 5. Управление автомобилем

Клиент → сервер, только в активной сцене:

```json
{
  "type": "input",
  "sceneId": "world:main",
  "epoch": 1,
  "seq": 12,
  "throttle": 1,
  "steering": -1,
  "brake": 0
}
```

- throttle: [-1, 1]; W = +1, S = -1, вместе = 0. Отрицательная тяга сначала
  замедляет движение вперёд, затем даёт задний ход; это решает Python-физика.
- steering: [-1, 1]; A = -1 (влево), D = +1 (вправо), вместе = 0.
- brake: [0, 1]; Space = 1. Тормоз останавливает машину, сам не включает задний ход.
  Если газ и тормоз нажаты вместе, тормоз имеет приоритет.
- seq начинается с 1 в каждой epoch и возрастает на каждую отправку, включая
  неизменившееся управление. Клавиши отпущены — продолжают отправляться нули.
  При потере фокуса клиент сразу отправляет throttle=0, steering=0, brake=1 и
  сбрасывает клавиши; серверная защита не зависит от доставки этого сообщения.
- Клиент не отправляет координаты или dt. Сообщение v1 `state` в v2 отклоняется.
- Сервер хранит последнюю принятую команду и применяет её на каждом шаге физики.
  Несколько команд до одного тика не создают дополнительные шаги и не ускоряют машину.
- Команды с неверными sceneId/epoch, повторным или меньшим seq игнорируются,
  не обновляют таймер активности и не изменяют состояние новой сцены.
- Нет свежего корректного input дольше inputTimeoutMs — throttle=0, steering=0,
  brake=1. При начале перехода ввод сбрасывается сразу, машина блокируется.
- Во время загрузки, до startTick и после завершения сценария input не применяется.
- Сервер ограничивает входящий поток 60 сообщениями/с на соединение; систематическое
  превышение закрывается кодом 1008 после сообщения `rate_limited`.

## 6. Snapshot — полное актуальное состояние видимых машин

Сервер → клиент:

```json
{
  "type": "snapshot",
  "sceneId": "world:main",
  "epoch": 1,
  "tick": 115,
  "players": [
    {
      "id": "p17", "name": "Ильяз", "vehicleType": "car", "roleId": null,
      "x": 1.25, "z": -3.4, "heading": 1.57, "speed": 4.2,
      "steering": 0, "wheelAngle": 0, "color": 3, "lastInputSeq": 12
    }
  ],
  "signals": []
}
```

`players` всегда включает себя. В общем мире включает остальных в области интереса,
выбранной сервером рядом с машиной; в сценарии — всех участников этого экземпляра.
Snapshot не содержит машины из других sceneId. Размер области интереса — настройка сервера.
Имя и тип машины включены в каждую запись, чтобы не зависеть от порядка отдельного
уведомления о появлении. `steering` — последнее применённое руление [-1, 1].
`wheelAngle` — фактический угол передних колёс в радианах после ограничения
на скорости; клиент использует его для поворота колёс. Положительный — вправо.
`color` — назначенный сервером при появлении индекс палитры кузова Kenney:
0 — зелёный, 1 — жёлтый, 2 — оранжевый, 3 — красный, 4 — синий.
Один индекс используется всеми клиентами; после нового подключения цвет может измениться.
`lastInputSeq` — максимальный seq, реально использованный физикой; до первого input — 0.

Высоту `y` и наклон `pitch` определяет сервер по опоре под осями. При потере
опоры действует гравитация; ближайший по высоте этаж не выбирается. Столкновения
с боксами объектов и машин учитывают высоту, поэтому нижний проезд не прикрепляет
машину к мосту. Невидимые боксы бордюров подняты на 2,5 м, проёмы между
участками открыты. Перемещение делится на подшаги до 20 см для контакта
с тонкими препятствиями. Клиент отправляет прежний `input` и отображает результат
из `snapshot`; дополнительные сетевые поля не нужны.

В v2 snapshot полный: новая запись создаёт модель, отсутствие чужого ID в следующем
snapshot удаляет модель из видимого набора.
Отдельные player_joined/player_left для v2 не требуются. Своя машина обновляется
по серверу, но не создаётся второй раз в модуле чужих машин.

`signals` — полный список динамических светофоров видимой области: объекты вида
`{"id":"signal-north","phase":"red"}`. Фазы: red, red_yellow, green, yellow, off.
Пустой список означает отсутствие светофоров. Переключения и проверку сигналов выполняет сервер.
Расположение, ориентация и принадлежность полосам находятся в данных карты.

Клиент принимает только сообщения своей sceneId/epoch и tick больше последнего
принятого. После scene_prepare история тиков новой сцены очищается. `tick` и состояние
передаются из одного согласованного шага, не из разных моментов симуляции.

## 7. Сцены, роли и готовность

Графический ресурс перекрёстка и игровая сессия разделены. Сценарий грузится в том же
приложении, с тем же canvas и WebSocket; переход не открывает новую вкладку.

Сервер → клиент, при первом входе и каждом переходе:

```json
{
  "type": "scene_prepare",
  "sceneId": "scenario:s42",
  "epoch": 2,
  "sceneKind": "scenario",
  "mapId": "junction-01",
  "scenarioId": "priority-01",
  "roleId": "truck_driver",
  "vehicleType": "truck",
  "spawn": { "x": 0, "z": -15, "heading": 0 },
  "participants": [
    { "id": "p17", "name": "Ильяз", "roleId": "truck_driver", "vehicleType": "truck" },
    { "id": "p18", "name": "Андрей", "roleId": "car_driver", "vehicleType": "car" }
  ],
  "plan": { "revision": 1, "chunkIds": ["junction-core"], "resources": [] },
  "timeoutMs": 30000
}
```

`sceneKind`: world или scenario. Для world: scenarioId=null, roleId=null;
participants может быть пустым — видимые игроки придут в snapshot. Для scenario
participants содержит точный состав и роли. Пример выше сокращён: реальный plan
содержит все ресурсы, нужные для первого кадра, в формате раздела 9.

При scene_prepare сервер уже зафиксировал переход и обнулил управление. Клиент:

1. Принимает только новую epoch; повтор той же подготовки не запускает вторую загрузку.
2. Отключает управление, показывает загрузку, очищает машины и интерполяцию старой сцены.
3. Отменяет прежние запросы и освобождает ненужные ресурсы с учётом бюджета.
4. Загружает и проверяет версии ресурсов, создаёт сцену и машину в spawn.
5. Отправляет scene_ready только после готовности плана целиком.

Клиент → сервер:

```json
{ "type": "scene_ready", "sceneId": "scenario:s42", "epoch": 2, "revision": 1 }
```

При ошибке:

```json
{
  "type": "scene_failed", "sceneId": "scenario:s42", "epoch": 2,
  "reason": "budget_exceeded"
}
```

Причины: budget_exceeded, download_failed, resource_mismatch, scene_build_failed.
Об успешной готовности нельзя сообщать до завершения загрузки.

Сервер ждёт готовности всех участников и отправляет каждому:

```json
{
  "type": "scene_start", "sceneId": "scenario:s42", "epoch": 2,
  "startTick": 240, "tick": 180
}
```

Участники одного сценария получают одинаковый startTick. До него сервер шлёт
неподвижные snapshot и не применяет input. Обратный отсчёт вычисляется по серверным
тикам, а не по совпадению часов ноутбуков. Первая реализация — 2 секунды отсчёта
для сценария, для общего мира достаточно следующего тика после scene_ready.
Если сообщение задержалось и startTick уже прошёл, клиент использует последний
snapshot, не проигрывает пропущенный отсчёт. Незагруженный участник не допускается к старту.

Первый snapshot новой сцены присылается сразу после scene_start, затем регулярно.
Ресурсы и машины новой сцены не смешиваются со старыми по совпавшим x/z.
Подтверждения старой epoch и повторные scene_ready игнорируются.

## 8. Зоны запуска, экземпляры и завершение задания

Зоны заданы на сервере в данных карты. Попадание определяет Python по положению
машины; клиент не отправляет «я в зоне». Первый вариант: игрок внутри зоны целиком,
|speed| ≤ 0.5 м/с непрерывно 1 секунду. Это игровые настройки, не норматив ПДД.
Точный размер зоны и количество участников находятся в её определении.

Сервер → ожидающему игроку в общем мире:

```json
{
  "type": "scenario_waiting", "sceneId": "world:main", "epoch": 1,
  "zoneId": "training-junction-01", "scenarioId": "priority-01",
  "waiting": 1, "required": 2
}
```

Выезд из зоны снимает ожидание; сервер отправляет scenario_waiting с waiting=0
этому игроку. Кандидаты упорядочены по времени готовности, при равенстве — по ID.
В один тик сервер атомарно выбирает пару, закрепляет роли и создаёт уникальный
sceneId. Один игрок не может находиться в двух сессиях. Третий остаётся в общем
мире; следующая пара может получить другой экземпляр того же сценария.

До перехода сервер сохраняет точку возврата, тип машины и старое состояние мира.
Затем исключает участников из snapshot общего мира и отправляет scene_prepare.
ID игроков остаются прежними. Назначение ролей фиксирует сервер, не порядок загрузки.

Состояния экземпляра: loading → countdown → running → finished или cancelled.
Ожидание пары происходит в общем мире до создания экземпляра. timeoutMs считается
по часам сервера. Ошибка загрузки, тайм-аут или выход одного участника отменяет
сценарий для остальных; единолично продолжать совместный сценарий в первой версии нельзя.
Шаблон задаёт timeLimitSeconds. Истечение игрового лимита завершает задание как
completed с passed=false для незавершивших участников; это не техническая отмена.

Серверная проверка правил создаёт события:

```json
{
  "type": "rule_event", "sceneId": "scenario:s42", "epoch": 2,
  "eventId": "event-19", "tick": 300, "playerId": "p17",
  "ruleId": "stop_required", "severity": "violation",
  "text": "Не выполнена требуемая остановка"
}
```

severity: info или violation. Событие с одним eventId учитывается и показывается
один раз. Времена пересечения и скорость берутся из физики на сервере, не из
частоты snapshot. Пересечение линии проверяется между предыдущим и текущим
положением машины, с её размерами; нельзя пропустить линию при большом шаге.
Приоритеты, условия остановки и завершения принадлежат Python-правилам конкретного
шаблона. Игровые допуски явно конфигурируются отдельно от текста правил ПДД.

Сервер → всем участникам:

```json
{
  "type": "scenario_result", "sceneId": "scenario:s42", "epoch": 2,
  "resultId": "result-42", "scenarioId": "priority-01", "status": "completed",
  "reason": null,
  "players": [
    { "id": "p17", "roleId": "truck_driver", "passed": false, "violationIds": ["event-19"] },
    { "id": "p18", "roleId": "car_driver", "passed": true, "violationIds": [] }
  ]
}
```

status: completed или cancelled. Для cancelled: passed=null, reason —
participant_left, load_timeout, load_failed или server_cancelled. Отмена по
технической причине не считается ошибкой ученика. Результат сохраняется один
раз по resultId, управление блокируется. Через 5 секунд сервер отправляет
scene_prepare общего мира с новой epoch. Клиент сам себя не телепортирует.
При возврате используется сохранённая точка рядом с зоной, но вне зоны активации;
машина остановлена, роль сброшена. Если точка занята — ближайшая свободная точка
возврата. Так не возникает бесконечного повторного запуска сценария.

## 9. Контент, HTTP и ограничение 10%

**Метрику требуется подтвердить у организаторов.** Командная трактовка: одновременно
доступные клиенту уникальные байты опубликованных ресурсов мира ≤ 10% суммарных
уникальных байтов того же набора контента. Это размеры файлов после снятия HTTP-сжатия,
а не размеры распакованных текстур/геометрии в RAM/GPU. Расход RAM/GPU измеряется отдельно.
Если организаторы требуют другую метрику, этот раздел меняется до приёмки кэша.

В набор входят общий мир, все сценарии, машины, знаки, текстуры и JSON-описания
уровней. Общий ресурс считается один раз по SHA-256. JS-код приложения, библиотеки,
сессии, текущие сетевые состояния и веса локальной LLM не увеличивают worldBytes.
Нельзя добавлять фиктивные файлы для искусственного увеличения знаменателя.
Небольшие управляющие манифесты-планы и bootstrap — метаданные протокола,
а JSON с содержимым/геометрией уровня — ресурс мира и учитывается.

`GET /api/v2/content/bootstrap`, после авторизации:

```json
{
  "worldId": "training-city", "contentVersion": "build-01",
  "worldBytes": 500000000, "cacheBudgetBytes": 50000000,
  "accounting": "unique_resource_bytes"
}
```

cacheBudgetBytes = floor(worldBytes × 0.1). При необходимости клиент выбирает
меньший рабочий лимит. Версия контента фиксируется на время соединения; при
несовместимом обновлении сервер завершает соединение кодом 4002, клиент
очищает старые планы, заново получает bootstrap и входит в актуальную версию.
Список всего мира клиенту не отправляется: сервер выбирает область по позиции.

Каждый plan в scene_prepare или chunks содержит revision, chunkIds и resources.
revision — возрастающий целый номер плана внутри epoch. resources — полный
набор уникальных ресурсов для активной области, включая общие модели и зависимости,
а не только новые файлы. Формат одного элемента:

```json
{
  "id": "road-crossing-model",
  "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "bytes": 5000000,
  "kind": "model",
  "url": "/api/v2/content/resources/road-crossing-model"
}
```

SHA в примере условный; в реальных данных это хеш именно указанного файла.
kind: model, texture или data. bytes — точное число байтов тела после HTTP-декодирования.
URL локальный, относится к contentVersion соединения и не меняет содержимое.
GLB самодостаточен либо все его внешние зависимости явно включены в resources.
Декодеры и библиотеки также локальны, но относятся к коду, не к миру.

При движении по миру сервер отправляет:

```json
{
  "type": "chunks", "sceneId": "world:main", "epoch": 1,
  "plan": {
    "revision": 2,
    "chunkIds": ["road-0-0", "road-0-1"],
    "resources": []
  }
}
```

resources здесь сокращён для примера. В реальном плане перечислен весь требуемый контент.
Сервер не делает новый план каждый тик: меняет его при изменении необходимого набора.
Клиент игнорирует устаревшие revision, отменяет устаревшие загрузки и подтверждает:

```json
{ "type": "chunks_ready", "sceneId": "world:main", "epoch": 1, "revision": 2 }
```

При ошибке — chunks_failed с теми же sceneId/epoch/revision и reason из scene_failed.
После неуспеха машина остаётся в прежней готовой области, сервер предлагает меньший
план либо показывает ошибку загрузки; нельзя молча разрешать движение в отсутствующий мир.
В сценарии первой версии весь перекрёсток входит в начальный plan и не стримится частями.

Переход между планами учитывает общий объём: старое активное + сохранённое + резерв
под новые загрузки ≤ budget. Резерв создаётся до начала запроса. Общая зависимость
учитывается один раз, ссылки от нескольких объектов не дублируют её бюджет.
Менеджер не сохраняет исходный ArrayBuffer после создания ресурсов без необходимости.
RAM/GPU-копии не складываются с размерами файлов в эту метрику, но освобождаются
вместе с неиспользуемым контентом. Удаление из сцены без освобождения ресурсов
не считается выгрузкой. Для общих ресурсов используется счётчик ссылок.

Первая реализация не использует постоянный кэш мира: Cache Storage и IndexedDB
для контента отключены, HTTP-ответы мира имеют `Cache-Control: no-store`.
Это не освобождает от учёта активной сцены в памяти приложения.

При смене сцены можно сначала выгрузить старую под экраном загрузки, затем скачать
новую. Во время движения сервер запрашивает соседние участки заранее и не допускает
машину за границу области, готовность которой подтверждена chunks_ready.
Должен существовать бюджет для перехода: сумма общих ресурсов, сохраняемого текущего
участка и минимальной следующей порции должна помещаться в 10%. Если это невозможно,
нужно уменьшить участки/ресурсы или скорость, а не временно превышать лимит.
Если сама минимальная сцена не помещается — scene_failed: budget_exceeded.

Диагностическая панель показывает worldBytes, budget, активные/сохранённые/зарезервированные
байты и процент. Объём определяется реестром ресурсов приложения, не общей квотой браузера.
Для сетевого/графического теста допустимы простые примитивы; соответствие 10% проверяется
на реальном опубликованном наборе контента, а не искусственном количестве пустых чанков.

## 10. Данные карты и сценария: контракт между авторами

Исходники Blender остаются исходниками, клиент получает GLB и JSON. Все данные
используют одинаковые оси, масштаб и начало координат. Масштаб модели автомобиля
применён при экспорте, размеры сверяются с конфигурацией физики.

Минимальные определения:

| Определение | Обязательное содержимое |
| --- | --- |
| Чанк | id, границы X/Z, ресурсы и объекты с assetId, x/z/heading |
| Дорога/полоса | id, направленная центральная линия, ширина, направление движения |
| Знак | id, тип, положение/ориентация и IDs полос, к которым относится |
| Стоп-линия | id, концы отрезка, нормаль разрешённого пересечения, IDs полос |
| Препятствие | id, форма box/circle, центр и размеры; для box также heading |
| Триггер | id, прямоугольник X/Z, scenarioId, requiredPlayers, точки возврата вне триггера |
| Конфликтная область | id, многоугольник X/Z и связанные маршруты |
| Шаблон сценария | scenarioId, mapId, timeLimitSeconds, роли, vehicleType, spawn для роли, маршрут/финиш, ruleIds и параметры |

Сервер читает глобальный каталог триггеров и физические/логические данные карты.
Клиент получает только нужные ему визуальные участки, а не весь каталог объектов.
JSON с физикой является общим источником размещения границ и линий: не вводить
отдельно вручную координаты в Python, отличающиеся от визуальной сцены.
Содержимое конкретного шаблона описывает автор сценария до его программирования.
Первая реализация включает одну плоскую карту и один сценарий на двух игроков.

## 11. Ошибки

Сервер → клиент:

```json
{
  "type": "error", "code": "bad_value",
  "text": "steering must be between -1 and 1",
  "refType": "input"
}
```

Обязательные поля: type/code/text; refType необязательное, если тип исходного
сообщения удалось прочитать. Клиент показывает текст в диагностике, не завершает
приложение из-за обычной ошибки. Сообщение с ошибкой не изменяет состояние игры.

Коды: bad_message, bad_value, unknown_type, not_joined, already_joined,
bad_version, not_authenticated, rate_limited, content_version_mismatch.
При bad_version сервер закрывает соединение кодом 1008; клиент не повторяет
бесконечно вход той же версией. Просроченные seq/epoch/revision игнорируются без
потока error. Неверный формат числа — bad_value, отсутствие обязательного поля — bad_message.
Входящие двоичные WebSocket-сообщения не поддерживаются (закрытие 1003),
превышение размера пакета — 1009. Транспортные ошибки не считаются нарушением ПДД.

## 12. Хранение и восстановление

SQLite находится только на сервере. Минимально сохраняются аккаунты и хеши паролей,
последняя безопасная позиция в общем мире, завершённые результаты с resultId,
нарушения и учебный прогресс. Сессионные токены не хранятся в виде открытых паролей.
Позиция периодически сохраняется и по нормальному выходу; результаты — сразу
транзакцией, повтор resultId не создаёт вторую запись.

Активные сценарии в первой реализации не восстанавливаются после обрыва. Вышедший
игрок возвращается при новом входе в безопасную точку общего мира, оставшийся
получает cancelled. После перезапуска процесса все незавершённые сессии считаются
отменёнными по технической причине, завершённые результаты сохраняются.
Не сохранять scenario-spawn как постоянную позицию общего мира.

## 13. Локальный инструктор: следующий этап исходного ТЗ

Сценарии ПДД не отменяют исходное требование об адаптивном ИИ. После базового
сценария инструктор объясняет ошибки с учётом сохранённого прогресса. Вычисления
и база знаний находятся на серверном ноутбуке; допускается локальная LLM или
адаптивный алгоритм без LLM. Готовая одинаковая реплика для всех не заменяет память.

Зарезервированные сообщения instructor_ask и instructor_reply пока не реализуются:
их точные поля добавляются отдельным дополнением до начала задачи. Генерация
не блокирует цикл физики, клиент не скачивает веса модели и всю базу знаний.
Результат scenario_result уже даёт серверу контекст ошибок без доверия к тексту клиента.

## 14. Параллельная разработка и приёмка

1. Автомобиль: Python step_vehicle и клиентский ввод/камера, без FastAPI внутри физики.
2. Карта: чанки, ресурсы и счётчик кэша, независимая проверка движением тестовой камеры.
3. Сервер: авторизация, /ws/v2, тик, сессии, snapshot, HTTP-контент и SQLite.
4. Сценарий: роли/правила на Python и клиентская загрузка по scene_prepare.

Владелец протокола вносит изменения в этот документ, остальные не меняют поля
самостоятельно. Общие места интеграции — сетевой адаптер и точка запуска клиента;
работа участников идёт в отдельных модулях. TS-типы и Python-схемы создаются
после фиксации контракта и проверяются одинаковыми JSON-примерами.

Порядок сборки: две машины на плоскости → ручной запуск сценария → автоматический
запуск из зоны → настоящая карта и приёмка кэша. HTTP/WS v1 остаются рабочими до
готовности v2. Переключение клиента на v2 — отдельный коммит с интеграционной проверкой.

Критерии приёмки:

- WebSocket без сессии не допускается к игре; reconnect не создаёт второго владельца аккаунта.
- input меняет машину на сервере; дополнительные пакеты не увеличивают скорость симуляции.
- Оба клиента видят согласованные машины, свою позицию также получают от сервера.
- Из двух участников получается один экземпляр; четыре участника могут получить два независимых.
- Без scene_ready обоих сценарий не стартует, у обоих одинаковый startTick.
- Старый input после телепортации и поздний HTTP-ответ не изменяют новую сцену.
- Выход/тайм-аут отменяет сценарий без учебного штрафа и возвращает оставшегося игрока.
- Нарушения определяются физикой на сервере, результат не дублируется и переживает перезапуск.
- Во время движения и перехода ресурсный счётчик вместе с резервом не превышает бюджет.
- Игра запускается в LAN с отключённым интернетом и локальными зависимостями.

## Высота дорожного полотна

В `scene_prepare.spawn` и каждой машине `snapshot.players` передаются
`y` (высота в метрах) и `pitch` (наклон в радианах; отрицательный — подъём
при движении вперёд). Сервер вычисляет их по поверхностям карты; клиент
интерполирует и применяет к модели вместе с x/z/heading. В `input` высота
не передаётся. Старые сообщения без этих полей трактуются клиентом как нули.
Позиция в SQLite сохраняется с высотой и worldId. При смене карты используется
новый spawn; на одной карте сохраняется выбранный уровень моста.

### Окружение и общий бюджет контента

В текущем плане машины один ресурс `car-kit/sedan.glb.bin`: gzip-контейнер
квантизованного GLB со встроенной PNG-палитрой. Общий контейнер модели загружается
один раз на сцену и используется всеми игроками. Это заменяет отдельные
`car-kit/sedan.glb` и `car-kit/Textures/colormap.png` в текущем `scene_prepare`.
`residentResources` манифеста описывает постоянные файлы; `worldBytes` включает
уникальные ресурсы карты, постоянные файлы и сам манифест. Bootstrap возвращает
те же worldBytes и бюджет floor(worldBytes/10). Клиент резервирует постоянные
ресурсы перед подгрузкой дороги, домов и пропсов. RAM/VRAM считаются отдельно
от размеров опубликованных файлов контента.

### Реализованный переход: left-turn

`Compact_003_road-intersection-path`: зона ожидания x=55..65, z=5..35,
по высоте y=-0.2..2.3. Внутри должен находиться весь бокс машины;
скорость не выше 0.5 м/с непрерывно одну секунду. Выезд или движение сбрасывают таймер.
Сервер выбирает первых двух готовых по времени остановки, затем playerId.
Первому назначается `left-turn`, второму `straight`; оба — легковые машины.
Знаки фиксированы: A/B главная, C второстепенная.

У пары уникальный `sceneId=scenario:left-turn:N`; epoch каждого увеличивается.
`scene_prepare.plan.mapManifestUrl` указывает на `/content/scenarios/left-turn/manifest.json`.
Клиент освобождает геометрию и ресурсы старой карты до загрузки новой.
Модели перекрёстка и подъездов используются из общего каталога.
Оба получают `scene_start` с одним startTick только после двух scene_ready.
Снимки игроков и физические столкновения ограничены sceneId.
Третий игрок остаётся в общем мире и может ждать следующую пару.
При отключении участника или превышении 30 секунд загрузки оставшиеся возвращаются
в сохранённые позиции общего мира через новый scene_prepare. В БД сохраняется
позиция общего мира, а не координаты упражнения. R в сценарии запрещена.
Сервер проверяет левый поворот: конфликт со встречным потоком, контакт автомобилей,
пересечение запрещённой разметки и заданный выход. В snapshot поле scenarioResult содержит
текст результата для получателя. Проверка приоритета использует фактический порядок полного выхода кузовов из перекрёстка:
сначала straight, затем left-turn. Порядок передаётся в passageOrder JSON-отчёта.
Каждому игроку scene_prepare передаёт личный finish (x,y,z,heading). Клиент рисует только свою арку.
После остановки в зоне личного финиша на секунду сервер возвращает игрока в общий мир
в фактическую позицию и направление на этом выезде; второй участник продолжает отдельно.
Движение или выход из зоны сбрасывают таймер. Текстовые подсказки скрыты.

Пересборка геометрии упражнения после изменения карты:
`python3 client/scripts/prepare-scenario.py`, затем перезапуск Python-сервера.

Готовые знаки упражнения: Dodecagon/Keet, CC0. Исходники — `blender/scenario-signs/`.
При изменении исходников сначала экспортировать через Blender:
`/Applications/Blender.app/Contents/MacOS/Blender -b --python client/scripts/export-scenario-signs.py`,
затем запустить `python3 client/scripts/prepare-scenario.py`.
